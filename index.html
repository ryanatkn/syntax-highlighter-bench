syntax-highlighter-bench

This is a benchmark of JS syntax highlighters: fuz_code, Twinkleplop, Prism, and Shiki with each of its two engines, run on the same inputs through one adapter each. It times throughput and cold start on one named machine, and measures bundle size, install footprint, retained memory, token counts, and output size, which come out the same on any machine with the same Node version.

The maintainer of this benchmark also maintains fuz_code, so that library is marked wherever it appears, every input is labeled by where it came from, and the method is published for anyone to reproduce.

The libraries have different features. Shiki highlights with the TextMate grammars and themes VS Code uses; Twinkleplop aims for a similar feature set, with its own themes, annotations, and Twoslash support; and both do more than fuz_code, which has the fewest features of the four: a single-pass lexer per language, with CSS classes for its theme. Their fidelity differs too: how finely each splits the same source, and how accurately it classifies each part. These numbers compare the work all of them share, not what one offers that another doesn't, and they time each library's output without scoring its quality.

What the numbers mean in practice

Whether a ratio matters depends on where the highlighting runs and how often. Which figure to read first:

  • At build time, as a static site or documentation build highlights its pages once: throughput sets the build's time and nothing else. Readers get plain HTML, so the JS and the cold start never reach them, though a theme stylesheet still does.
  • In the browser: everything a page loads and the cold start to a first highlight come first, then throughput on long pages.
  • In an editor that highlights as you type: throughput at the size being edited, against the time of one frame.
  • On a server that renders each request: throughput and retained memory, paid on every request and held by every process.
  • In serverless and edge functions: the cold start, paid by every fresh instance, and the bundle where the platform limits its size.

The HTML throughput worked out for sizes a reader knows. Each figure applies the geometric-mean rate over the neutral inputs to that size, so it is an estimate; a library's rate differs from input to input, as the results page shows.

What each language costs

What each language's grammar costs, in two ways. The first language is the JS a page loads for that language alone, minified and compressed with gzip, less the library with no language: it includes any runtime the language needs that the floor leaves out, which a library pays once, and any language it loads with it, as when a library's TypeScript loads its JS. One more language is what the language adds to a bundle that already holds every other timed language, in minified bytes: the price of adding it to a site that has the rest. A language the others already hold, like JS inside TypeScript, adds little or nothing there. The bars of each group are on one scale, and beside a number is its ratio to the smallest in the row; a row where a library adds nothing has no ratios.
